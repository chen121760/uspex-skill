# Is the run dead, or still working?

> Load this when: a search has been quiet for a long time, one core per run is pinned at 100 %,
> `still_running` is sitting in the run directory, or a fixed-threshold check (`uspex_status.py`
> with its default `--stale-minutes 30`) says `stalled`. Killing a live search and babysitting a
> dead one are the two expensive mistakes; this file is the triage that separates them.

## Why "no output" is not a death test

Four properties of a real run make silence weak evidence. All four were observed on an audited
10.5.0 (08/07/2021) installation driving 3D variable-composition code-99 searches.

1. **The evolutionary algorithm executes inside the engine process.** `uspex.x` hosts the embedded
   MATLAB runtime: the busy thread's stack names `mcr_run_main`, `Mfh_MATLAB_fn::dispatch_fh`,
   `mx_array_api::mxSetArrayScope`, `icu_56::MessageFormat`, while `matlab_helper` is a separate
   child that mostly sits in `pipe_read` at ~0 % CPU. "One core at 100 %, `matlab_helper` idle" is
   therefore the *normal* state — during structure generation **and** during a dead loop. CPU
   usage never separates the two.
2. **Every generation has a long, genuinely silent phase.** After `Calculating fitness in <t> sec`
   the engine ranks the population and evolves the next generation without touching disk. A
   healthy run was measured at **21.5 min of complete file silence** (no `write`, no `openat`, no
   mtime change) before it dumped `results*/generation<N>/`, `POOL.mat`, `Pareto_ranking`,
   `compositionStatistics`, `E_series.pdf`, `Variation-Operators.pdf`, and only then began printing
   `Structure <n> generated by heredity` / `built with the symmetry group ...`.
3. **`still_running` is not a hang indicator.** USPEX writes it on entering the MATLAB engine
   phase and removes it when that invocation returns; its own text says it is present either
   because MATLAB is still running or because MATLAB exited with an error. An invocation that is
   killed (or that dies) leaves it behind forever. `still_reading` is the different, documented
   marker used by the restart gate (`references/seeds-restarts.md`).
4. **The driver log is a poor heartbeat.** The usual driver does `date > log; USPEX -r >> log`, so
   the log is truncated at every invocation, and engine stdout redirected to a file is
   block-buffered. A rolled banner plus a changed size means "another invocation started"; silence
   means nothing at all.

Because the driver loop waits on its `USPEX -r` child, one dead invocation blocks the loop: the
directory can look "supervised" for days while nothing advances.

## Step 1 — measure this run's own cadence

Never judge silence against a constant. Measure how long *this* run normally takes per generation,
then compare.

```bash
python scripts/check_run_liveness.py RUN_DIR --sample-seconds 90     # does steps 1–3 and prints next actions
```

Its cadence source is the completion time of each finished generation, from
`results*/generation<N>/` directory mtimes, with `CalcFoldTemp/Jobs.history` submission times as a
fallback when those directories are absent. The same numbers by hand:

```bash
ls -d  RUN_DIR/results*/generation*  | xargs -r stat -c '%Y %y %n' | sort -n | tail -8
grep -o 'Submitted [A-Za-z][a-z][a-z][0-9]*-[0-9:]*' RUN_DIR/CalcFoldTemp/Jobs.history | tail -8
```

Across sibling runs of one real project the generation cadence was **1.5 h, 2.2 h, 2.9 h and
3.7 h** — a 2.5× spread, which is exactly why a fixed staleness threshold cannot be right for all
of them. Use the median interval, floor it at ~15 min, and treat it as the budget for one quiet
phase.

## Step 2 — sample the engine for movement

Two short samples decide whether the CPU is producing anything:

```bash
pid=$(for p in $(pgrep -f 'src/uspex.x'); do [ "$(readlink /proc/$p/cwd)" = "$RUN_DIR" ] && echo $p; done)
awk '{print $14+$15}' /proc/$pid/stat          # CPU ticks (100/s) — sample twice
grep -E '^(rchar|wchar|write_bytes)' /proc/$pid/io   # bytes touched — sample twice
cat /proc/$pid/wchan ; ps -T -p $pid -o spid,stat,pcpu,time,wchan
find RUN_DIR -maxdepth 2 -newermt '-30 minutes'      # any artefact change at all
```

Reading the sample:

| Observation over ~60–120 s | Meaning |
|---|---|
| `rchar`/`wchar` climbing by MB, files changing, generation dirs appearing | working — do not touch it |
| CPU ticks climbing ~100/s, `rchar`/`wchar` flat, no file mtime changes, no job of this run in the scheduler | **the dead signature**: user-space spin with no output |
| thousands of `futex` calls/s in `timeout 5 strace -f -c -p $pid` and nothing else | spin (a `restart_syscall`/`nanosleep` or two per second is its heartbeat) |
| occasional `mmap`/`munmap` churn plus a few `futex`, still no I/O | an allocation-retry loop; still unproductive if it lasts past the cadence budget |
| `eu-stack -p $pid` hot thread in MATLAB frames | the engine is executing, which is normal — combine with the I/O line above, never with CPU alone |

`eu-stack`/`gdb`/`strace` are optional: the cadence-versus-silence comparison plus the I/O sample
is enough for the verdict. They are what turns "it is probably dead" into "this is a spin loop
inside the MATLAB engine".

## Step 3 — verdict

`check_run_liveness.py` returns one of these (exit codes in parentheses, and it prints the evidence
it used):

| Verdict | Evidence | Action |
|---|---|---|
| `done` (0) | `USPEX_IS_DONE`, or `OUTPUT.txt` records the finish | analyse results |
| `working` (1) | artefacts/IO moved in the sample window, **or** job(s) of this run are active, **or** silence is below this run's own cadence | nothing; re-check around cadence/2 |
| `working` + warning | silence between 1× and 3× cadence | re-check now; corroborate with queue state before waiting longer |
| `stuck` (2) | engine alive, silence past 3× cadence, no I/O movement, no active job | triage the cause, then recover (below) |
| `stopped` (3) | no engine and no driver for this directory, not finished | needs a restart, not a kill |
| `unknown` (4) | no artefacts, or the directory is not a run root | point it at the directory holding `INPUT.txt` |

Cross-check with the artefact/state view before acting — they answer different questions:

```bash
python scripts/uspex_status.py RUN_DIR --stale-minutes 240   # state, generations, per-structure evidence
```

Reconcile disagreements in favour of the cadence measurement: `uspex_status.py` calls a run
`stalled` purely from a fixed silence threshold, so on a 3.7 h/generation search its default
30 min threshold is 7× too tight. Pass a `--stale-minutes` above the run's own quiet-phase budget.
A useful sanity pair from the audited project: the dead run's last artefact was **34 h** old
(≈18× its own 1.9 h cadence) with frozen I/O; two healthy siblings were quiet for **21 min**
(0.23×) and **84 min** (0.38×) and both continued.

## If it is dead — first tell the user why (do not silently restart)

Never report "it crashed" without an interpretation, and never restart before preserving evidence.
Collect `log`/`uspex-driver.log`, `nohup.out`, `Warnings`, the helper's stderr target, and the
offending `CalcFold*`, then read them for the cause:

| Evidence | Possible interpretation |
|---|---|
| `nohup.out` or the driver log contains `MATLAB:badsubscript` with a trace through `SoftModeMutation_301` → `EA_301` → `Start` → `USPEX` (`EA_*`/`SoftModeMutation_*` are the MATLAB EA routines, suffixed by `calculationType`) | the MATLAB side died on a particular structure/variation operator — a soft-mode mutation on a structure whose mode indices are out of range. The engine then busy-waits forever; the loop cannot recover. |
| `still_running` present, `matlab_helper` blocked in `pipe_read`, engine spinning in `futex` with frozen I/O | engine↔helper handshake deadlock, usually downstream of a MATLAB error above (the helper never receives the next request; the engine never sees a reply) |
| `Warnings` / `ERROR-OUTCAR-Gen*-Ind*-Step*` / per-structure stage logs carry engine errors | the failure is per-structure, not global: some individuals legitimately become `999999.000` sentinels; only a run that cannot finish a generation is broken |
| no engine process, driver log ends with `exit=` or nothing, jobs still terminal | the driver died between invocations (`run_uspex_loop.sh` failures, SSH death, an `exit 1` from a wrapper) — restart the loop, not the search |
| `df -h`, `dmesg`, `ulimit`, quota messages | disk full / OOM / inode exhaustion: fix the resource first, then branch A |
| the engine disappeared right after a scheduler job ended | status-callback or ingestion fault — see `references/submission.md` and the callback rows in `references/errors.md` |

Write that interpretation into the hand-off so the next session does not repeat the triage.

## Recovery: three branches

Precondition for **all three**: prove no writer is still alive — no `uspex.x`, no `USPEX -r`, no
`matlab_helper` whose cwd is this run, and no scheduler job of this run
(`check_run_liveness.py` prints exactly that proof; confirm with `squeue -u $USER`/`qstat -u $USER`).

| Branch | Choose it when | Do |
|---|---|---|
| **A — continue in place** | the cause is understood or transient, the `*.mat` state is intact, and the last completed generation is complete in its `results<f>/` | `rm -f still_running still_reading`, run one foreground `USPEX -r`, confirm it does real work, then re-attach the detached loop |
| **B — pick-up restart** | the state is suspect, the failure reproduces, or the run was killed mid-generation | record `Warnings`; `USPEX --clean`; set `pickUpYN = 1`, `pickUpGen = <last complete generation>`, `pickUpFolder = <f>`; one foreground `USPEX -r` into a new `results<N>`; verify it before re-attaching the loop |
| **C — fresh start** | the attempt is abandoned, or the chemistry/settings have changed | `USPEX --clean` and relaunch; keep the old `results*/` folders for the record |

```bash
# A (the common case after a MATLAB-phase death)
rm -f still_running still_reading
USPEX -r                       # foreground: watch it ingest, rank, and emit new structures
nohup setsid ./01-<name> >> /dev/null 2>&1 &     # or assets/run_uspex_loop.sh
```

Details of `--clean`, the `pickUp*` scalars, the completeness gate for the source generation and
the checklist are in `references/seeds-restarts.md`; run it from the original run directory and
never hand-delete `CalcFold*`, state files, or scheduler logs to force a stuck run forward.

Two notes specific to this failure mode:

- **`still_running` is cleared as part of branch A** because every subsequent check must be able to
  trust that marker, and the stale copy from a dead invocation is not evidence of anything. On the
  audited 10.5.0 install the manual only documents `still_reading` for a plain re-run, so treat
  `still_running` removal as local practice gated on the same no-live-writer proof — not as a
  documented lock.
- **If the cause was not fixed, branch A will hang again at the same point.** Expect to repeat the
  triage; if it reproduces on the same operator, consider starting branch B from a generation before
  the offending structure, or reducing the offending `frac*`/soft-mutation weight in `INPUT.txt`
  and recording it as a deliberate change.

## Guardrails

- Do not kill a run because of a fixed staleness threshold, a pinned core, a leftover marker, or an
  empty queue: all four are expected mid-cycle.
- Do not restart while any engine, driver, helper, or job of that run is alive — two writers corrupt
  the same `*.mat` state.
- Do not present `stuck` as a diagnosis on its own: give the user the evidence, the interpretation,
  and the branch you recommend, and let them confirm before processes are killed.
